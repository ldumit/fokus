# CLAUDE.md Merge Protocol

How to merge the kit's CLAUDE.md.template into an existing project's CLAUDE.md.

## Principle

The target's CLAUDE.md is the base document. The kit adds pipeline sections — it never removes target content silently. The user's stack-specific content is preserved; the kit's workflow infrastructure is layered in. Any section the kit replaces is announced to the user at CHECKPOINT 1 before the merge happens.

## Greenfield Shortcut

If no CLAUDE.md exists in the target:
1. Copy `CLAUDE.md.template` to `CLAUDE.md`
2. Remove the generation metadata comment (`<!-- Generated by export-cc-setup ... -->`)
3. Prompt user to fill each `<!-- FILL: ... -->` marker via `AskUserQuestion`
4. Done — no merge needed

## Section Classification

Read the kit's CLAUDE.md.template. Each `##` section falls into one of three types:

### FILL marker sections
Sections containing a `<!-- FILL: {description} -->` marker. Detected dynamically by scanning the template for `<!-- FILL:` — not hardcoded to a fixed list. The export may templatize any section (Tech Stack, Frontend, Repo Structure, Architecture, authentication specifics, etc.).

**Detection:** Scan the template for every `##` section that contains `<!-- FILL:`. Each is a FILL marker section regardless of its header name.

**Merge rule:**
1. Check if target's CLAUDE.md has a `##` header matching this section. Match algorithm:
   - **Exact match** first (case-insensitive): "## Tech Stack" = "## Tech Stack"
   - **Alias match** second, using this table for common mismatches:
     | Kit section | Also matches |
     |-------------|-------------|
     | `## Tech Stack` | `## Stack`, `## Technology`, `## Technologies` |
     | `## Frontend` | `## UI`, `## Client`, `## Front-end`, `## Front End` |
     | `## Repo Structure` | `## Project Structure`, `## Directory Structure`, `## Folder Structure` |
     | `## Architecture` | `## Architectural Patterns`, `## Design Patterns` |
   - For sections not in the alias table, use exact header match only
   - If no match by either method, treat as "no match"
2. If match found: extract target's section content, replace the FILL marker with it. Show the result at CHECKPOINT 1 for confirmation.
3. If no match: prompt the user to provide content via `AskUserQuestion`, using the FILL marker's description and examples as guidance.

### Pipeline sections (kept as-is in template)
Sections describing workflow patterns, guardrails, and conventions — no FILL marker, not project-specific.

**Examples:** `## Guardrails`, `## Port Convention`

**Merge rule:**
1. If target doesn't have this section -> add it. Place it in a logical position: `## Architecture` near the top, `## Guardrails` after architecture, operational sections after that.
2. If target has the same `##` header with compatible content (additive) -> merge, preferring kit version for pipeline content.
3. If target has the same `##` header with conflicting content -> **announce the conflict to the user at CHECKPOINT 1**: show both versions, explain that the kit version will replace it, and that the original is archived. Then replace with kit version during Phase 3.

### Removed sections
Sections the export removed because they were project-specific to the source project (e.g., graphify config, tool-specific integrations). These don't appear in the template.

**Merge rule:** Do not add these to the target.

## Conflict Detection

A section "conflicts" when:
- Same `##` header exists in both kit template and target
- Content differs beyond whitespace
- The section is a pipeline section (not a FILL marker section)

Conflicts are always announced — never silently resolved. The user sees:
```
**CLAUDE.md conflict: ## {Section Name}**
Your version: {summary or first 3 lines}
Kit version: {summary or first 3 lines}
Action: Kit version replaces yours. Original archived.
```

## Handling Target Content That Affects the Kit

Scan the target's CLAUDE.md for content that could conflict with the kit's pipeline assumptions:
- Agent behavior overrides (e.g., "never use subagents" conflicts with kit agents that delegate)
- Contradictory guardrails (e.g., "always write comments" vs kit's "default to no comments")
- Workflow instructions that duplicate or conflict with kit's pipeline protocol

For each detected conflict, include it in the CHECKPOINT 1 report:
```
**Warning:** Your CLAUDE.md contains "{conflicting text}" which may conflict
with the kit's {agent/rule/convention}. This section will be preserved as-is,
but you may want to adjust it after import.
```

## Section Ordering

After merge, don't enforce a rigid order — adapt to the target's existing structure:
1. Target's original sections stay in their current positions
2. Kit pipeline sections are inserted where they logically fit
3. If the target has no structure to follow, use the kit template's order

## Post-Merge Cleanup

- Remove the kit's generation metadata header comment
- Ensure no duplicate `##` headers exist
- Verify no raw FILL markers remain (all should be resolved)
