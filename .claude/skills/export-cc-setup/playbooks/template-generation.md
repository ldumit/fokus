# Template Generation Playbook

How to transform the source project's CLAUDE.md into a portable template with fill-in sections.

## Process

1. Read the source CLAUDE.md fully
2. Classify each `##` section
3. Transform per classification
4. Add header comment
5. Write to `{output-path}/CLAUDE.md.template`

## Section Classification

Read each `##`-level section and classify:

### Keep as-is (portable content)

Sections describing workflow mechanics that transcend any specific stack or project:

- **`## Guardrails`** — behavioral rules. Clean any tech-specific guardrails into generic versions. Keep the guardrail structure.
- **`## Port Convention`** — if the convention is a generic numbering scheme, keep it. If it references Docker/K8s specifics, templatize the technology-specific parts.

### Templatize (replace body with FILL markers)

Sections whose content IS the stack or IS the project's architectural philosophy:

- **`## Tech Stack`** — this IS what changes between projects. Replace entirely with a FILL marker.
- **`## Frontend`** — same. Replace entirely.
- **`## Repo Structure`** — folder structure varies by stack. Keep the section header, replace the tree and descriptions with a FILL marker.
- **`## Architecture`** — architectural patterns (DDD, CQRS, etc.) are stack-independent but project-specific. Each project chooses its own patterns. Replace with a FILL marker that includes the source's patterns as one example.

### Templatize if present

Sections that may or may not exist in a given project:

- Service-specific sections (naming specific services, databases, infrastructure)
- Authentication/authorization specifics (the mechanism varies by stack)
- Build/deployment specifics

### Remove

Sections with no template value for other projects:

- External tool integration configs specific to this project (e.g., `## graphify` with a project-specific graph path)
- Sections that are purely current project state documentation

**When removing:** only remove if the section has zero portable value. If it has a portable concept with project-specific details, templatize instead.

## FILL Marker Format

Each FILL marker is a markdown comment block with:
1. The section name
2. What to put there (1-2 sentence description)
3. Example content from a DIFFERENT stack than the source

```markdown
<!-- FILL: Tech Stack
List your project's technology stack. Include: language/runtime, web framework,
ORM/data access, message broker (if any), authentication, API documentation tool.

Example (Python):
- Python 3.12 / FastAPI
- SQLAlchemy + PostgreSQL
- Celery + Redis for async tasks
- JWT authentication via python-jose
- OpenAPI via FastAPI built-in

Example (Go):
- Go 1.22 / Gin
- GORM + PostgreSQL
- NATS for messaging
- JWT middleware
- Swagger via swaggo
-->
```

**Why examples from different stacks?** To avoid implying the source stack is the default. Two examples from different ecosystems show the user what level of detail to provide.

## Header Comment

Add at the very top of the template file:

```markdown
<!--
  Claude Code Setup Kit - Template CLAUDE.md
  Generated by export-cc-setup v{version} on {YYYY-MM-DD}
  Source: {project-name} (stack-independent extraction)

  Instructions:
  1. Copy this file to your project root as CLAUDE.md
  2. Fill in every <!-- FILL: ... --> section with your project's details
  3. Delete this header comment and all FILL markers when done
  4. See INSTALL.md for the complete setup checklist
-->
```

## Structural Rules

- **Never invent sections.** Only templatize or keep sections that exist in the source. The kit reflects the source setup's structure — if the source has no `## Frontend`, the template won't have one either.
- **Preserve section order.** Keep sections in the same order as the source.
- **Keep markdown formatting.** If the source uses tables, the template uses tables. If it uses bullet lists, keep bullet lists.
- **Clean intra-section references.** If a kept section references a templatized section (e.g., "see Tech Stack above"), the reference still works since the section header is preserved.

## Edge Cases

- **Nested sections (`###`):** If a `##` section is kept but contains `###` subsections that are stack-specific, templatize only the stack-specific subsections.
- **Sections with mixed content:** If a section has both portable and stack-specific paragraphs, keep the portable paragraphs and templatize only the stack-specific ones. Use inline FILL markers.
- **Very short CLAUDE.md:** If the source has only 2-3 sections and all are stack-specific, the template will be mostly FILL markers. This is correct — the portable value comes from `.claude/`, not from CLAUDE.md.
