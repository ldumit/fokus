## System Shape

Fokus is a single-service web application that syncs sprint data from Jira's REST API and computes analytics locally. It is part of the Agentic Rituals Suite but deploys independently.

```
┌─────────────┐         ┌─────────────────────┐         ┌──────────┐
│  Browser    │◄───────►│  Fokus (App Service) │────────►│ Jira API │
│  (Vue SPA)  │  HTTP   │  .NET 10 + SQLite   │  HTTPS  │  (Cloud) │
└─────────────┘         └─────────────────────┘         └──────────┘
```

Single service, three-project split:

```
src/Services/Fokus/
  Fokus.API/           # Host, FastEndpoints feature slices, Jira client, DI
  Fokus.Domain/        # Aggregates, value objects, enums
  Fokus.Persistence/   # DbContext, configs, migrations, repositories
client/                # Vue 3 SPA source (builds to API's wwwroot/)
```

Reference graph:
```
API ──► Domain
 │
 └──► Persistence ──► Domain
```

No separate Application project — FastEndpoints endpoint classes own feature slices directly.

## Architectural Decisions

### DDD with Vertical Slice Architecture

**Decision:** Domain-Driven Design with vertical slice feature organization. Each feature is a self-contained folder in `{Svc}.API/Features/` containing endpoint, request, response, validator, and event handlers.
**Rationale:** Fokus has clear aggregate boundaries (Sprint, Ticket) and distinct feature areas (Sync, Dashboard, Developers, Sprints, Epics, Settings). Vertical slices keep related code together; DDD keeps domain rules in the domain layer.
**Constraints:** No service layer classes. No god folders. Domain rules enforced in aggregates, not handlers.
**Skill reference:** `create-feature`, `domain-patterns`
**Not specified here:** Endpoint class structure, request/response naming, validator wiring, handler logic organization — owned by `create-feature`. Aggregate base class shape, entity equality, value object patterns, partial class split, event dispatch — owned by `domain-patterns`.

### CQRS (Lightweight)

**Decision:** Command/query separation at the endpoint level. Write operations (sync) mutate domain entities via repositories. Read operations (analytics) query the database and compute metrics. No MediatR, no separate command/query handler classes in v1.
**Rationale:** Fokus has a clean write/read split (sync vs analytics) but low complexity — MediatR pipeline would be overhead with no cross-cutting behaviors to justify it. FastEndpoints handlers are the command/query handlers.
**Constraints:** If cross-cutting behaviors are needed later (logging, validation pipelines, caching), introduce MediatR at that point.
**Skill reference:** `create-feature` (endpoint-as-handler pattern)
**Not specified here:** MediatR command/query handler patterns — owned by `cqrs-patterns` (not applicable in v1). Endpoint structure — owned by `create-feature`.

### Sync-from-External Domain Model

**Decision:** Domain entities are populated by syncing from Jira, not created by user actions. Entities use natural keys from the source system (Sprint.Id = Jira sprint ID, Ticket.Key = Jira issue key, Developer.AccountId = Jira account ID). Sync is idempotent — re-syncing overwrites with fresh data.
**Rationale:** Fokus is an analytics dashboard over Jira data. The domain doesn't originate data; it mirrors and enriches it. Natural keys eliminate mapping layers and make sync idempotent by design.
**Constraints:** Entities that would normally use auto-increment IDs instead use externally-assigned keys. Upsert semantics required on all sync paths. SprintMembership uses composite key (SprintId, TicketKey).
**Skill reference:** `domain-patterns`, `create-aggregate`
**Not specified here:** AggregateRoot/Entity base class hierarchy, ValueObject base types, domain event variants, backing collection pattern — owned by `domain-patterns`. Full aggregate creation workflow — owned by `create-aggregate`.

### Computed Metrics (Never Stored)

**Decision:** All analytics metrics (health scores, throughput, cycle times, scope change rates, carry-over rates, bug ratios, epic projections) are computed per-request from raw synced data. No precomputed aggregation tables.
**Rationale:** Dataset is small (hundreds of tickets per sprint, not thousands). Computing on-the-fly keeps sync idempotent (overwrite raw data, metrics recompute automatically) and eliminates stale-cache risks. Add materialization only if query performance degrades.
**Constraints:** Query endpoints must compute both current value and delta vs. previous sprint in a single request. All metric responses use `{ value, delta, direction }` shape.
**Skill reference:** `analytics-computation-service`
**Not specified here:** Records, delta/direction helpers, multi-sprint iteration, sparkline builders, rolling average — owned by `analytics-computation-service`.

### Concrete Repositories (No Interfaces)

**Decision:** Repositories are concrete classes, not interfaces with implementations.
**Rationale:** Single implementation per repository — interfaces add indirection with no polymorphism benefit. This is a project guardrail.
**Constraints:** Each repository wraps `SaveChangesAsync` so endpoints never touch `DbContext` directly.
**Skill reference:** `persistence-patterns`
**Not specified here:** Repository base class, entity configuration base, DbContext registration, interceptor wiring — owned by `persistence-patterns`.

### FastEndpoints as Framework

**Decision:** FastEndpoints for HTTP endpoints with built-in FluentValidation integration.
**Rationale:** Clean endpoint-per-feature model. Validators are sibling classes in the same folder, auto-discovered and executed pre-handler. Pre/post processors available for cross-cutting concerns.
**Constraints:** No minimal API endpoints. No controllers. One endpoint class per feature action.
**Skill reference:** `create-feature`
**Not specified here:** Endpoint base class selection, Configure() conventions, validator registration, request/response naming — owned by `create-feature`.

### Frontend: Vue 3 SPA

**Decision:** Vue 3 + TypeScript + Pinia + Tailwind CSS + ApexCharts. Built with Vite into `wwwroot/`, served as static files by the .NET host. No full UI kit.
**Rationale:** Lightweight SPA stack. Dashboard is read-heavy with chart-heavy views — ApexCharts handles the visualization. Tailwind keeps styling co-located. Pinia provides typed state management. Single-solution monorepo (no separate deployment).
**Constraints:** No Vuetify, no PrimeVue. `shadcn-vue` acceptable if lightweight. Dark theme default, light theme toggle. Responsive: 1440px primary, 1024px laptop.
**Skill reference:** `vue-patterns`, `vue-component-architecture`, `pinia-patterns`, `tailwind-theme`, `create-vue-feature`
**Not specified here:** Composition API patterns, component hierarchy, store boundaries, Tailwind theme tokens, feature slice scaffolding — owned by the respective skills.

## Cross-Cutting Concerns

### Error Handling

**Approach:** Global exception handler via FastEndpoints. Jira API errors surface as typed error responses (401 invalid credentials, 502 unreachable). Domain guard utilities for invariant enforcement.
**Skill reference:** `error-handling`
**Not specified here:** Exception class hierarchy, Guard utility API, global middleware registration, problem details format — owned by `error-handling`.

### Logging

**Approach:** Structured logging via `ILogger<T>`. Sync operations logged (start, counts, duration, errors). Console + App Service logs only in v1.
**Skill reference:** None (see Gaps)
**Not specified here:** N/A — no logging skill exists.

### Security

**Approach:** No user authentication in v1 — single-user tool on private App Service. Jira credentials never exposed via API. CORS same-origin. Scalar UI gated to Development.
**Skill reference:** `authorization-patterns` (not applicable in v1, ready for later)
**Not specified here:** Role gate + resource gate patterns — owned by `authorization-patterns` (for when auth is added).

### SignalR (Real-Time Push)

**Approach:** ASP.NET Core SignalR hub per feature area. Hub classes live in `Fokus.API/Hubs/`. `IHubContext<THub>` is injected into endpoints that trigger broadcasts. Hub method name constants defined as static classes alongside the hub. Broadcast is best-effort (wrapped in try/catch — failure must not break the triggering operation).
**Current hubs:** `SprintHub` at `/hubs/sprint` — broadcasts `SprintSynced` after a successful sprint sync.
**Frontend:** `@microsoft/signalr` HubConnectionBuilder. SignalR lifecycle (connect/disconnect) managed in Pinia stores, not components. Store starts connection on tab enter, stops on tab leave or component unmount.
**Skill reference:** None (see Gaps)

### API Documentation

**Approach:** `Microsoft.AspNetCore.OpenApi` (built into .NET 10) + Scalar (`Scalar.AspNetCore`) for interactive UI. No Swashbuckle.
**Skill reference:** None
**Not specified here:** N/A — framework-provided, no custom pattern needed.

## Domain Model

### Classification

| Entity | Role | Key Strategy | Rationale |
|--------|------|-------------|-----------|
| Sprint | Aggregate root | Jira sprint ID (int) | Owns SprintMemberships; sync boundary |
| Ticket | Aggregate root | Jira issue key (string, e.g. "PROJ-1234") | Owns StatusTransitions; independent lifecycle |
| Developer | Entity | Jira account ID (string) | Identified by external system; SubTeam is app-managed |
| SprintMembership | Child entity of Sprint | Composite (SprintId, TicketKey) | No meaning outside a Sprint |
| StatusTransition | Child entity of Ticket | Auto-increment int | No meaning outside a Ticket |
| AppSettings | Standalone entity | Single row | Application configuration, not a domain concept |

### Value Objects

| Value Object | Storage | Purpose |
|--------------|---------|---------|
| HealthThresholdConfig | Persisted (JSON column on AppSettings) | Green/amber/red boundaries per metric |
| HealthWeightConfig | Persisted (JSON column on AppSettings) | Weights for composite health score |
| HealthScore | Computed (never stored) | Weighted composite 0-100 |
| StageDuration | Computed (never stored) | Time in one workflow stage for one ticket |
| MetricWithDelta | Computed (never stored) | Any metric value + delta vs. prior sprint |

### Relationships

```
Sprint ──1:N──► SprintMembership ◄──N:1── Ticket
                                           │
Ticket ──1:N──► StatusTransition            │
                                           ▼
Developer ◄──N:1── Ticket (via AssigneeId)
```

### Design Notes

- **Thin domain in v1.** Entities are data containers synced from Jira. Business logic lives in metric computation (query-side endpoints). As features grow (F6+ analytics with workflow rules, carry-over policies), behavior methods will move into aggregates.
- **No domain events in v1.** Sync is a write-overwrite operation with no downstream reactions within the service. When analytics features need reactive behavior (e.g., recalculate health score when sync completes), domain events will be introduced following `domain-patterns` Variant B (aggregate reference only).
- **Delta pattern.** All metric query responses include current value + delta vs. previous sprint (signed number + direction). The API computes the same metric for sprint N and N-1 in a single query.

### HealthScore Formula

```
score = 100
score -= (1 - completionRate) * completionWeight
score -= disruptionRate * disruptionWeight
score -= carryOverRate * carryOverWeight
clamp(0, 100)
```

Default weights: completion = 40, disruption = 30, carry-over = 30. Configurable via AppSettings.

## Deployment & Infrastructure

### Azure App Service (Linux)

- Single App Service instance (B1 tier)
- SQLite file in persistent storage (`/home/data/fokus.db`)
- Vue SPA served as static files from `wwwroot/`
- Azure Key Vault for secrets via Managed Identity
- No separate database server

### Secrets

| Key | Source | Description |
|-----|--------|-------------|
| `Jira:InstanceUrl` | Key Vault / User Secrets | e.g. `https://acme.atlassian.net` |
| `Jira:Email` | Key Vault / User Secrets | Account email for API auth |
| `Jira:ApiToken` | Key Vault / User Secrets | Atlassian API token |

### Runtime Settings (SQLite)

User-configurable via Settings UI. Stored as typed `AppSettings` entity (single row, JSON columns for complex values).

| Setting | Type | Purpose |
|---------|------|---------|
| BoardId | int? | Which Jira board to sync |
| DoneStatuses | string[] | Statuses that count as "done" |
| WorkflowStages | string[] | Ordered workflow stages for cycle time |
| HealthThresholds | HealthThresholdConfig | Green/amber/red boundaries |
| HealthWeights | HealthWeightConfig | Composite score weights |

### Build & Deploy

```
dotnet publish → single self-contained binary + wwwroot/
```

### Key Indexes

| Table | Index | Purpose |
|-------|-------|---------|
| SprintMembership | PK (SprintId, TicketKey) | Composite key, sprint queries |
| SprintMembership | IX_TicketKey | Carry-over analysis |
| StatusTransition | IX_TicketKey_Timestamp | Cycle time computation |
| Ticket | IX_EpicKey | Epic progress queries |
| Ticket | IX_AssigneeId | Developer throughput queries |

- Multi-board support (single board in Settings)
- GitHub integration
- Export (PDF/PNG)
- User authentication (single-user deployment)

- gRPC (no service-to-service calls)
