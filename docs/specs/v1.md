# Sprint Health Dashboard — Product Specification

**Owner:** Laurentiu  
**Status:** Draft  
**Date:** May 4, 2026  
**Suite:** Agentic Rituals Suite — lightweight companion tool  

---

## 1. What It Is

A standalone web dashboard that reads from the Jira REST API and surfaces the cross-sprint, per-developer, per-epic analytics that Jira cannot produce natively. Built for Scrum Masters managing split teams on limited Jira tiers.

**Dual purpose:**
- **Team tool** — solves real sprint tracking pain for Laurentiu's team
- **Career showcase** — demonstrates the ability to rapidly build useful internal tooling

**What it is not:**
- Not a Jira replacement or plugin
- Not a marketplace app constrained by Jira's rendering model
- Not a real-time monitoring tool — it analyzes closed sprints

---

## 2. Target User

Scrum Master or Engineering Manager who:
- Manages a team split across multiple sub-teams
- Uses Jira (any tier, including Free/Teams) for sprint management
- Needs per-developer and cross-sprint analytics that Jira doesn't provide
- Wants data-backed arguments for stakeholders about scope changes and capacity

## 3. Data Source

### 3.1 Jira REST API Endpoints

| Endpoint | Purpose |
|---|---|
| `GET /rest/agile/1.0/board/{boardId}/sprint` | List all sprints for a board |
| `GET /rest/agile/1.0/sprint/{sprintId}` | Sprint metadata (dates, state) |
| `GET /rest/agile/1.0/sprint/{sprintId}/issue?expand=changelog` | All issues in a sprint with full changelog |
| `GET /rest/api/3/issue/{issueKey}?expand=changelog` | Individual issue detail with status transitions |
| `GET /rest/agile/1.0/board` | List boards (for initial setup) |

### 3.2 Authentication

Basic Auth with Atlassian API token. User provides:
- Jira instance URL (e.g., `https://acme.atlassian.net`)
- Email address
- API token (generated at https://id.atlassian.com/manage-profile/security/api-tokens)

Stored locally in the app's configuration. Never transmitted elsewhere.

### 3.3 Sync Model

- **Manual trigger** — user clicks "Sync Sprint" in the UI, selects a sprint
- **Backfill** — "Sync All Closed Sprints" for first-time setup
- **Idempotent** — re-syncing the same sprint overwrites with fresh data
- **No scheduler in v1** — user syncs after closing a sprint in Jira
- **Active sprint sync** — allowed but flagged as "in progress" (data will change)

### 3.4 Rate Limiting

API token-based traffic uses burst rate limits only (per-second throttle), not the points-based quota system. A typical sprint sync of 50 issues with changelogs requires ~50-60 API calls. At 10 requests/second with backoff, this completes in under 10 seconds. No risk of hitting limits.

## 4. Domain Model

Five entities. No stored aggregates — all metrics compute on the fly.

### 4.1 Sprint

```
Sprint
├── Id              int (Jira sprint ID)
├── Name            string ("Sprint 27")
├── StartDate       DateTime
├── EndDate         DateTime
├── BoardId         int
├── BoardName       string
├── State           enum (Active, Closed)
├── SyncedAt        DateTime (last sync timestamp)
```

### 4.2 Developer

```
Developer
├── AccountId       string (Jira account ID, PK)
├── DisplayName     string
├── AvatarUrl       string (nullable)
├── SubTeam         string (nullable — manually tagged in app)
├── IsActive        bool (soft delete for people who leave)
```

SubTeam is the only field not sourced from Jira. Managed via a simple admin screen.

### 4.3 Ticket

```
Ticket
├── Key             string ("PROJ-1234", PK)
├── Summary         string
├── IssueType       string (Story, Bug, Task, Sub-task)
├── StoryPoints     decimal (nullable — not all tickets have SP)
├── EpicKey         string (nullable)
├── EpicName        string (nullable)
├── AssigneeId      string (FK → Developer.AccountId)
├── Priority        string
├── CurrentStatus   string
├── CreatedDate     DateTime
├── ResolvedDate    DateTime (nullable)
```

### 4.4 SprintMembership

The pivot table that makes everything work. One row per ticket per sprint.

```
SprintMembership
├── SprintId        int (FK → Sprint.Id)
├── TicketKey       string (FK → Ticket.Key)
├── AddedAt         DateTime (when ticket was added to this sprint)
├── RemovedAt       DateTime (nullable — if removed mid-sprint)
├── WasCommitted    bool (was in sprint at Sprint.StartDate)
├── FinalStatus     string (ticket's status when sprint closed)
├── StoryPoints     decimal (snapshot at sync time — SP can change)
```

**WasCommitted logic:**
- `true` if `AddedAt <= Sprint.StartDate`
- `false` if `AddedAt > Sprint.StartDate` (mid-sprint addition = scope change)

**WasCommitted** and **FinalStatus** are retained as stored fields but no longer drive scope attribution (see Sprint scope attribution below).

**Sprint scope attribution:** Both cycle time boundaries (`CycleTimeStartStage` and `CycleTimeEndStage`) control how tickets are attributed to sprints via StatusTransition timestamps. A ticket is *started/active* in the sprint where it first transitions to `CycleTimeStartStage` (or any stage after it in the ordered `WorkflowStages` sequence). A ticket is *completed* in the sprint where it first transitions to `CycleTimeEndStage` (or any stage after it). Each transition belongs to exactly one sprint — no double-counting of carry-over tickets. Scope metrics are feature-only; bug metrics have dedicated surfaces.

For example, if CycleTimeStartStage = In Progress and CycleTimeEndStage = Testing: a ticket that moves to In Progress in Sprint 26 and to Testing in Sprint 27 is *active* in Sprint 26 and *completed* in Sprint 27. Its SP count once for each.

### 4.5 StatusTransition

```
StatusTransition
├── Id              int (auto)
├── TicketKey       string (FK → Ticket.Key)
├── FromStatus      string
├── ToStatus        string
├── Timestamp       DateTime
├── AuthorId        string (who made the transition)
```

Sprint association is derived: join on Timestamp between Sprint.StartDate and Sprint.EndDate.

## 5. Features

### 5.1 Developer Throughput

**Question:** "How many story points can each developer deliver per sprint?"

**Metric:** For each developer, per sprint: count of tickets completed (FinalStatus in Done category), sum of SP completed, completion rate (completed SP / assigned SP).

**Display:** Table with columns: Developer | Sub-Team | SP Assigned | SP Completed | Completion % | Tickets Done | Tickets Carried Over. Multi-line chart showing all developers across last N sprints on the same axes. 3-sprint rolling average per developer.

**Edge cases:**
- Ticket reassigned mid-sprint → attribute to the assignee at sync time (the person who has it when the sprint closes)
- Ticket with no SP → count in ticket count, exclude from SP metrics
- Developer with zero tickets in a sprint → show as zero, don't hide them

---

### 5.2 Sprint Scope Change & Disruption Analysis

**Question:** "Why didn't we finish everything? What got added mid-sprint?"

**Metrics:**
- **Committed SP** — sum of SP where WasCommitted = true
- **Added SP** — sum of SP where WasCommitted = false AND RemovedAt is null
- **Removed SP** — sum of SP where RemovedAt is not null
- **Net scope change** — Added SP - Removed SP
- **Disruption rate** — Added SP / Committed SP × 100

**Disruption classification** (derived from IssueType + WasCommitted):
| Category | Rule |
|---|---|
| Unplanned bug | IssueType = Bug AND WasCommitted = false |
| Scope injection | IssueType = Story/Task AND WasCommitted = false |
| Priority escalation | WasCommitted = false AND ticket existed before sprint start (CreatedDate < Sprint.StartDate) |
| Net-zero swap | Ticket added AND different ticket removed in same sprint (detect by SP proximity) |

**Display:**
- Stacked bar chart per sprint: committed (gray) + added (orange) + removed (red) + completed (green)
- Disruption timeline: horizontal bar showing which day of the sprint items were added — day 1-2 = planning overflow, day 5+ = real disruption
- Trend line of disruption rate across sprints — the chart you show your managers
- Breakdown table by disruption category with SP totals

---

### 5.3 Carry-Over Tracker

**Question:** "How much work rolls from sprint to sprint, and where does it get stuck?"

**Metrics:**
- **Carry-over SP** — sum of SP where FinalStatus not in Done category
- **Carry-over rate** — Carry-over SP / (Committed SP + Added SP) × 100
- **Status distribution of carry-over** — group carry-over tickets by FinalStatus (e.g., 60% stuck in Testing, 25% still In Progress)
- **Repeat offenders** — tickets that appear in SprintMembership for 3+ sprints

**Display:**
- Carry-over rate trend across sprints (line chart)
- Per-sprint pie chart showing where carry-over tickets are stuck
- "Zombie tickets" table: tickets that have lived through 3+ sprints with their full sprint history

---

### 5.4 Cycle Time (In Progress → Testing)

**Question:** "How long does actual development take once someone picks up a ticket?"

**Metric:** Duration from StatusTransition where ToStatus = "In Progress" to StatusTransition where ToStatus = "Testing" (or equivalent status names — configurable).

Compute per ticket, then aggregate: average, median, P90 per sprint, per developer, per issue type.

**Display:**
- Box plot per sprint showing distribution (not just average — outliers matter)
- Per-developer average cycle time with trend sparklines
- Outlier flags: any ticket 2x+ the sprint median, listed separately
- Breakdown by issue type (bugs typically faster than stories)

**Configuration needed:**
- User maps their Jira workflow statuses to the cycle time boundaries: "cycle starts at" (default: In Progress) and "cycle ends at" (default: Testing/QA/Review)

---

### 5.5 Bug Ratio Per Developer

**Question:** "Who's spending their sprint on bugs vs. features?"

**Metrics:**
- Per developer per sprint: count of Stories completed, count of Bugs completed, bug percentage
- SP on bugs vs. SP on stories/tasks

**Display:**
- Per-developer stacked bar: features (blue) vs. bugs (red) per sprint
- Team-level trend: overall bug SP as percentage of total SP across sprints
- Alert if a developer's bug ratio exceeds 50% for 2+ consecutive sprints

---

### 5.6 Epic Progress

**Question:** "How's this epic actually going? When will it be done?"

**Metrics:**
- Per epic: total tickets, tickets done, tickets remaining, total SP, SP done, SP remaining
- Completion percentage (by ticket count and by SP — both, since they tell different stories)
- Active sprints (how many sprints this epic has had tickets in)
- Velocity on this epic (SP completed per sprint, last 3 sprints)
- Projected sprints to completion (remaining SP / epic velocity)

**Display:**
- Progress bar per epic with SP done / SP total
- Table: Epic | Total SP | Done SP | % Done | Sprints Active | Projected Remaining
- Expandable rows showing individual tickets per epic with status

---

### 5.7 Sprint Summary Card

**Question:** "Give me the whole sprint in 30 seconds."

A single-screen overview per sprint, designed for retrospectives and stakeholder updates.

**Contents:**
- Sprint name, dates, duration
- Health score indicator (green/amber/red based on completion rate + disruption rate + carry-over rate thresholds)
- Four metric cards: SP Completed / Committed | Completion % | Disruption Rate | Carry-Over Rate
- Top 3 epics progressed (by SP completed)
- Developer leaderboard (SP completed, sorted descending — no gamification, just visibility)
- Flags: zombie tickets, high-disruption days, developers with 0 SP completed

**Health score thresholds (configurable):**
| Metric | Green | Amber | Red |
|---|---|---|---|
| Completion rate | ≥ 80% | 60-79% | < 60% |
| Disruption rate | < 20% | 20-40% | > 40% |
| Carry-over rate | < 15% | 15-30% | > 30% |

## 6. UI Structure

### 6.1 Navigation

Sidebar navigation with:
- **Dashboard** — Sprint Summary Card (default landing page)
- **Developers** — per-developer throughput, bug ratio, cycle time
- **Sprints** — scope change, disruption analysis, carry-over
- **Epics** — epic progress and projections
- **Settings** — Jira connection, sub-team tagging, workflow status mapping, health thresholds

Global controls in the header:
- Sprint selector (dropdown: specific sprint or "Last 3" / "Last 5" / "All")
- Sub-team filter (All / Sub-team name)

### 6.2 Design Direction

- **Dark theme default** (with light theme toggle) — dashboard aesthetic, professional
- **Card-based layout** — each metric in its own card with proper breathing room
- **Health indicators** — colored dots or badges (green/amber/red) on every card
- **Smooth transitions** — ApexCharts animations on data load and filter change
- **Responsive** — works on large monitors (primary) and laptop screens
- **No clutter** — 5-7 metrics visible per screen, drill-down for details

### 6.3 Visual References

- **Hatica Sprint Performance Dashboard** — signal cards + per-developer breakdown + cycle time chart. Closest overall layout reference.
- **LinearB** — individual contributor sparklines, clean developer comparison tables.
- **Harness SEI** — ratio-based health signals with thresholds, flow chart diagnostics.

## Revisions

### Rev 1 — 2026-05-10: Done category definition

**What changed:** Added explicit definition of "Done category" in §4.4 (SprintMembership). Completion is now defined as FinalStatus at or after `CycleTimeEndStage` in the configured `WorkflowStages` order — not a static list of statuses.

**Why:** The original spec used "Done category" without defining it, leading to an implementation that hardcoded `DoneStatuses: ["Done", "Closed"]` as a separate setting. This broke the intended flexibility: cycle time boundaries should control what "completed" means across all analytics. The burnup chart showed artificially low completion numbers because tickets in Testing (or other intermediate-done stages) were not counted.

**Impact:** All features that reference "Done category" or "completed" (§5.1 Throughput, §5.2 Scope Change, §5.3 Carry-Over, §5.5 Bug Ratio, §5.6 Epic Progress, §5.7 Sprint Summary Card) derive their completion definition from this single source. A new feature (F22) covers the implementation change.

### Rev 2 — 2026-05-10: Transition-based sprint scope attribution

**What changed:** Replaced snapshot-based scope attribution (WasCommitted flag, FinalStatus) with transition-based attribution using StatusTransition timestamps and both cycle time boundaries. CycleTimeStartStage now defines "started/active" scope. CycleTimeEndStage completion is now transition-based (first transition during sprint window) instead of position-based (FinalStatus at sprint end). All scope surfaces are feature-only with separate bug surfaces.

**Why:** Snapshot-based attribution double-counted carry-over tickets — a ticket In Progress in Sprint 26 that completed in Sprint 27 counted as committed in both sprints. The cycle time boundaries should be the universal control for all sprint analytics: widening (To Do → Done) approximates traditional tracking, narrowing (In Progress → Testing) measures dev throughput, with no double-counting either way.

**Impact:** All features that use committed/active/completed scope (§5.1 Throughput, §5.2 Scope Change, §5.3 Carry-Over, §5.5 Bug Ratio, §5.6 Epic Progress, §5.7 Sprint Summary Card) derive attribution from StatusTransition timestamps and both cycle time boundaries. Supersedes Rev 1's position-based FinalStatus completion. A new feature (F23) covers the implementation change.
