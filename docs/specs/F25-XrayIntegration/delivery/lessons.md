# Xray Integration & Ticket Test Enrichment — Lessons

## PO Lessons

- **Critic caught API pattern conflicts the PO missed.** The spec referenced `PUT /api/settings` (monolithic) and `/api/sync/sprint` (singular) — both wrong. The codebase uses per-section save endpoints and `/api/sync/sprints` (plural). Lesson: when a spec defines API surfaces, the critic's codebase-aware review (Phase 2.5) is essential. Cross-check mode wouldn't have caught these since the PO agent doesn't read source code.

- **Edge cases from the source spec need explicit transfer.** v2.md §5.1 had four edge cases (multi-TE tickets, multi-ticket TEs, multi-run TEs, sub-task inheritance) that weren't carried into the feature spec. The critic flagged all four. Lesson: when extracting a feature spec from a larger product spec, systematically transfer edge cases — they're easy to skip when focusing on the happy path.

- **Infrastructure-only scope needs explicit dependency declarations.** The spec initially said F4 "includes issue link reading" — it doesn't. The Jira module has zero issue link support. Lesson: when a feature depends on extending an existing module, state that the extension is IN SCOPE for this feature, not an assumed pre-existing capability.

- **The "no GraphQL client library" decision from v2.md is a tech constraint that sits on the boundary between spec and plan.** The critic flagged it as MEDIUM. It was omitted because the spec voice rules exclude framework internals. But "no additional dependency" is a product-level constraint (avoids dependency bloat), not just a code pattern. Leaving it in Out of Scope as a tech note keeps it visible without violating voice rules.

## Architect Lessons

- **Critic review caught real dependency ordering issues.** The original plan had DI wiring as Step 16 (last) but endpoints in Steps 10-13 required `IXrayClient` to be registered. Critic finding #5 correctly identified this. Lesson: when planning module creation, the DI wiring step must be ordered immediately after the module implementation step, not at the end. The natural impulse is "wire up last" but DI registration is a compile-time dependency for all consumers.

- **Method signature consistency needs a single-source declaration.** The critic caught that Step 11 declared `List<Ticket>` while Step 13 said "pass JiraIssue list directly." The root cause: the sync service signature was first written in Step 11 (the service definition) but the actual input type was only clear from Step 13/14 (the callers). Lesson: define the service method signature in terms of its callers' available data, not in terms of what feels natural for the service. Both callers had `JiraIssue` objects, so `IReadOnlyList<JiraIssue>` was the only correct signature.

- **When a plan defers a query to a future feature, name the method and describe the join path.** The critic flagged BR 3 (sprint attribution tiebreaker) as ambiguous because the plan said "derived at query time" without specifying who implements it. Adding the forward reference with a concrete method signature (`GetTestExecutionsForSprintAsync`) and join strategy made the F26 handoff unambiguous. Lesson: forward references to future features should include the method name and data path, not just "F26 will handle it."

- [TRACKED] **Secret preservation requires explicit handler step ordering in the plan.** The `SaveAsync` method uses `SetValues` which overwrites all properties. If the endpoint handler sets `existing.XrayClientSecret = req.XrayClientSecret` (which is null for "no change" requests) before calling `SaveAsync`, the secret is destroyed. The critic correctly identified that the plan needed to spell out the exact conditional-set-before-save sequence. Lesson: when a save pattern uses `SetValues`, any field with "preserve if not provided" semantics needs explicit handler ordering in the plan, not just a note.

- **Standalone sync endpoint validator vs. frontend mismatch is a plan gap.** The plan specified a sprint selector in the UI (Step 16) and a validator requiring non-empty SprintIds (Step 13). The developer simplified the UI by omitting the selector but kept the validator, creating a functional contradiction (frontend sends `[]`, validator rejects `[]`). The plan should have been explicit about what happens when the user wants to sync all sprints -- either the validator allows empty (meaning "all"), or the UI must provide selection. Flagging this for the reviewer as a code-level issue.

## Developer Lessons

- **Microsoft.Extensions.Http must be explicit for non-Refit projects.** Xray.GraphQL uses IHttpClientFactory/AddHttpClient but does not use Refit. Jira.RestApi gets these types transitively through Refit, but new module projects that don't use Refit need `<PackageReference Include="Microsoft.Extensions.Http" Version="..."/>` explicitly, or the build fails with CS0234/CS0246 on the Microsoft.Extensions namespace.
- **Xray auth response is a raw quoted JWT string.** The Xray Cloud `/api/v2/authenticate` endpoint returns the bearer token as a raw JSON string literal (e.g., `"eyJ..."`), not a JSON object with a token field. Response body must be deserialized as `string` and trimmed of surrounding quotes.
- **SyncBacklogSprintsResponse Xray field needs fully qualified type.** Adding `XraySyncSummary? Xray` to `SyncBacklogSprintsResponse` required using the fully qualified `SyncSprints.XraySyncSummary` to avoid namespace conflicts, since the class lives in the `SyncSprints` namespace and the response is in `SyncBacklogSprints`.
- **Per-section save pattern is consistent and predictable.** The existing SettingsView pattern of per-panel save state refs (`xraySaving`, `xraySaved`, `xrayError`) is well-established — follow it exactly for new sections rather than inventing shared save-state abstractions.
- **Sync QA Data frontend scope.** When the standalone Xray sync endpoint loads its own sprint scope server-side, the frontend sends an empty `sprintIds: []` to trigger a full sync. Per-sprint QA sync selection can be added in F26+ if needed.

## Reviewer Lessons

- [TRACKED] **Empty-list short-circuit guards in clients can silently break probe queries.** `GraphQLXrayClient.GetTestExecutionsAsync` correctly short-circuits on empty `issueKeys` for production sync, but this same guard turns the TestConnection probe into a no-op. When a client method is reused for both "real work" and "health check" purposes, the two call sites have different requirements: production callers want the fast-return, probe callers need the actual network roundtrip. Either overload the method or add a dedicated probe method. Flag this pattern whenever an endpoint's acceptance criteria includes "verifies both auth AND data access."

- [TRACKED] **Scoped service with instance-level state is a subtle runtime bug.** `GraphQLXrayClient` is scoped but carries rate-limit counters as instance fields. The build passes and the feature works in single-request testing — the bug only manifests under concurrent load. Review DI lifetime vs. state lifetime explicitly for any service that maintains counters, caches, or accumulators. When a plan says "track X across requests," the holding object must be singleton (or use a singleton helper).

- **When a plan deviation removes a UI element that a validator depends on, it creates a broken feature.** The developer's deviation (omitting sprint selector) and the validator (`NotEmpty()`) were written independently and not reconciled. During review, always cross-check plan deviations in implementation.md against the validator rules in the affected endpoint. A UI simplification that removes the only source of a required field is a breaking change.

- **`SetValues` self-copy analysis is non-obvious but safe.** The `AppSettingsRepository.SaveAsync` passes the same EF-tracked entity back as both `settings` and `existing` (via identity map). The `SetValues(settings)` call is effectively a no-op when source and destination are the same tracked instance. This looked like a secret-overwrite risk during pre-commitment prediction but is safe. Worth documenting in the repository method as a comment to prevent future confusion.
