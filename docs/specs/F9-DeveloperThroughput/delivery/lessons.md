# Developer Throughput — Lessons

## Architect Lessons
- [TRACKED] Rolling average window expansion is a non-obvious requirement: when the user requests "last 3 sprints", the endpoint must load additional prior sprints beyond the requested range to compute 3-sprint rolling averages. This lookback need must be explicit in the plan -- it changes the data loading strategy from "load exactly what was requested" to "load requested + lookback window."
- [TRACKED] The PageToolbar aggregate options ("Last 3", "Last 5", "All") introduce a mode-switching pattern that affects both the toolbar component and the consuming store. The plan must specify backward compatibility: existing consumers (DashboardView) must not break when the toolbar gains new capabilities gated behind a prop.
- [TRACKED] DeveloperSprintCapacity as a standalone entity (not owned by Developer aggregate) is the right call because: (a) Developer is Entity<string> not AggregateRoot, so it cannot own collections via DDD conventions; (b) capacity is queried in bulk by sprint, not always through the developer; (c) the composite key pattern already exists with SprintMembership.
- [TRACKED] When planning delta computation, explicitly state which sprint is "prior" in both single and multi modes. In multi-sprint mode deltas are suppressed entirely -- this is a spec decision, not an implementation shortcut.
- [APPLIED] When response DTOs will be consumed by frontend CRUD operations (not just display), include the entity identifier in the response shape. The plan omitted `AccountId` from `DeveloperThroughputEntry`, but the frontend needed it to call the PUT capacity endpoint. Plan response shapes should be validated against all consuming actions, not just the display table.
- [TRACKED] Pre-commitment predictions for Step 1: predicted frontend gaps and migration confirmation as likely issues. Actual result was clean -- all 12 steps covered with only minor justified deviations. The developer's implementation report was thorough and well-structured, which made the done check straightforward. Good implementation reports reduce review friction significantly.

## Reviewer Lessons
- [TRACKED] When a plan uses a sub-team filter at two levels (FilterDevelopers + GetDeveloperMemberships), verify whether the second filter is logically redundant given the first. If the filtered developers are iterated and their memberships fetched by AssigneeId, and Assignee IS the Developer entity, the sub-team check on memberships is always true for those developers. Redundant but harmless — do not flag higher than LOW.
- [APPLIED] `required` keyword on int properties in plain data entities is worth checking: int has a default value of 0 which can silently produce an invalid FK record. For composite key members, `required int` is more defensively correct than plain `int`, even though EF will enforce the FK at persist time.
- [TRACKED] Pre-commitment predictions are highly effective for this pattern of feature (analytics service + CRUD endpoints + frontend view): the most likely failure areas are rolling average edge cases, delta null handling, and store initialization order. Investigate all three even when the implementation looks clean.
- [TRACKED] The `sprints[0]` index for "most recent sprint" is correct only because `GetClosedSprintsAsync` returns `OrderByDescending(StartDate)`. Future reviewers: always verify sort direction when `[0]` is used to mean "most recent."
