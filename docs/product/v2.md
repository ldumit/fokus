## 1. What It Is

An extension to the Sprint Health Dashboard that integrates Xray Cloud test management data, enriching every sprint ticket with its test coverage and execution results. Gives Scrum Masters and Engineering Managers the quality dimension they're currently missing — "was this sprint actually tested, and did it pass?"

**What it adds:**
- Per-ticket test coverage and pass/fail status from Xray
- Sprint-level QA health metrics (coverage rate, pass rate, execution progress)
- Per-QA-member workload and execution throughput
- Cross-sprint quality trends with deltas and sparklines
- QA health as a sub-score in the existing sprint health score

**What it is not:**
- Not a test management tool — Xray owns test authoring and execution workflows
- Not a replacement for Xray's UI — QA engineers still work in Xray day-to-day
- Not an automated test runner — the team does manual testing, Fokus reads the results

**Feature flag:** The entire QA module is gated behind a boolean setting. When disabled, no QA UI elements appear and no Xray API calls are made.

---

## 2. Target User

Same as v1 — Scrum Master or Engineering Manager — now with additional needs:

- Wants to know which stories in a sprint have been tested and which haven't
- Needs data-backed arguments about quality, not just delivery velocity
- Wants to see QA workload distribution across the team
- Needs cross-sprint quality trends for retrospectives and stakeholder conversations
- Cannot get sprint-level QA aggregation from Xray's native reports (Xray reports are per test plan/execution, not per sprint)

**Secondary user:** QA Lead who wants to see their team's execution throughput and coverage gaps correlated with sprint context.

## 3. Data Source

### 3.1 Xray Cloud GraphQL API

Primary endpoint: `https://xray.cloud.getxray.app/api/v2/graphql`

| Query | Purpose |
|---|---|
| `getTestExecutions` | Fetch test executions with their test runs and statuses — **primary entity** |
| `getTestRun` / `getTestRunById` | Fetch individual test run results (PASS/FAIL/TODO/EXECUTING) |
| `getTestSets` | Fetch test set groupings (organized by feature area) |
| `getTestPlans` | Fetch test plans (organized by version/milestone) — secondary |

All queries support JQL filtering (e.g., filter by project, sprint labels).

**Note:** The team does not create standalone "Test" issues — the `getTests` query returns zero results. All testing flows through Test Executions and Test Sets linked directly to stories.

**Key nested traversal (single GraphQL call):**
```
Test Execution → Test Runs → Status (PASS/FAIL/TODO/EXECUTING)
```

Story → Test Execution linkage is via Jira issue links (`tests` / `is tested by`), read from the Jira API during sprint sync. The Xray GraphQL API provides the test run details (pass/fail counts) that Jira cannot access.

### 3.2 Xray Authentication

Separate from Jira's Basic Auth. Xray Cloud uses its own API key system.

User provides:
- **Client ID** — from Xray Global Settings → API Keys
- **Client Secret** — from Xray Global Settings → API Keys

Authentication flow:
1. `POST https://xray.cloud.getxray.app/api/v2/authenticate` with `{ client_id, client_secret }`
2. Receive a bearer token (expires after 24 hours)
3. Use bearer token in `Authorization` header for all GraphQL requests

API keys do not expire. Bearer tokens expire after 24 hours and must be refreshed.

### 3.3 Xray Sync Model

- **Triggered alongside sprint sync** — when a sprint is synced from Jira, Xray data is fetched for all tickets in that sprint (if Xray is enabled)
- **Also triggerable independently** — "Sync QA Data" button refreshes Xray data for the currently selected sprint without re-syncing Jira data
- **Idempotent** — re-syncing overwrites with fresh data from Xray
- **Graceful degradation** — if Xray credentials are invalid or Xray is unreachable, the sprint sync completes normally for Jira data and logs a warning for QA

### 3.4 Rate Limiting

| Tier | Limit |
|---|---|
| Xray Standard | 300 requests / 5 minutes |
| Xray Enterprise | 1,000 requests / 5 minutes |

GraphQL pagination: 1–100 items per connection, max 10,000 items per call, max 25 resolvers per call. JQL filter results capped at 100 issues per query.

A typical sprint of 30 stories with linked tests requires 2–5 GraphQL calls (batched by story, nested traversal for test runs). Well within rate limits.

### 3.5 Linking Model (validated against live data)

Xray creates a `Test` link type with labels:
- **Outward:** `tests` (TE/Test Set → Story direction)
- **Inward:** `is tested by` (Story → TE/Test Set direction)

Additionally, Test Executions use `Blocks` / `is blocked by` links to tie discovered bugs back to the TE.

**How entities connect in this project:**
```
Story ←──(is tested by)──→ Test Execution  ──→  Test Runs (PASS/FAIL, via Xray API)
                           │
                           └──(is blocked by)──→ Bugs (defects found during execution)

Story ←──(is tested by)──→ Test Set  (groups tests by feature area)

Test Plan  (standalone, named by version/milestone, no issue links)
```

**Key findings from audit:**
- **No standalone Test issues exist** — the "Test" issue type is registered but unused. All testing flows through Test Executions and Test Sets.
- **Test Plans have no issue links** — no epic links, no story links. Named by version/milestone convention (e.g., "v6 E2E | Test Plan", "V6 Blue Ocean"). Cannot be traversed programmatically to epics.
- **Test Sets link to stories/requirements** via the `tests` link type and are organized by feature area (Dashboard, Verification, Green Bean, etc.).
- **Test Executions link to stories** via the `tests` link type. Some also have sprint field (`customfield_10020`) but it's **inconsistently populated**.
- **Sprint association is derived:** since the sprint field on TEs is unreliable, Fokus derives the TE's sprint from the linked story's sprint membership. If TE `tests` story PD-5228 and PD-5228 is in Sprint 28, then the TE belongs to Sprint 28.

### 3.6 Dual-API Sync Strategy

Xray data requires **two API sources** working together:

1. **Jira REST API** (already used by v1) — during sprint sync, read `issuelinks` on each ticket to discover linked Test Executions and Test Sets. Also read the `Blocks` links on TEs to discover bugs found during testing. This gives us the coverage graph (which tickets have TEs, which TEs found bugs).

2. **Xray GraphQL API** (new) — for each discovered Test Execution, fetch the test runs and their statuses (PASS/FAIL/TODO/EXECUTING). This data is Xray-internal and not accessible via the Jira API.

**Sync flow:**
```
Sprint Sync (Jira API)
  └─ For each ticket, read issuelinks
       └─ Collect linked TEs and Test Sets (link type = "Test")
            └─ For each TE, read issuelinks for Blocks (bug links)
  └─ Xray Sync (GraphQL API)
       └─ For each discovered TE, fetch test runs + statuses
       └─ Store results locally
```

## 4. Domain Model

Four new entities. Extends the v1 domain model — existing entities (Sprint, Ticket, Developer, etc.) are unchanged. The Developer entity is reused for QA members (no separate QaMember — the audit showed QA and dev roles overlap on the same people).

### 4.1 TestExecution

The primary QA entity. Represents a Test Execution issue from Xray, linked to stories via the `tests` issue link type.

```
TestExecution
├── IssueId         string (Xray internal ID, PK)
├── IssueKey        string (Jira issue key, e.g., "PD-5384")
├── Summary         string
├── Status          string (Jira issue status: To Do, In Progress, Done, Cancelled)
├── AssigneeId      string (FK → Developer.AccountId — who ran the execution)
├── CreatedDate     DateTime
```

### 4.2 TestExecutionLink

The pivot between tickets and their linked test executions. One row per ticket-TE link. Also captures bug links discovered during execution.

```
TestExecutionLink
├── TestExecutionIssueId  string (FK → TestExecution.IssueId)
├── TicketKey             string (FK → Ticket.Key)
├── LinkType              enum (Tests, Blocks)
```

- `Tests` = TE tests this story (coverage)
- `Blocks` = this bug was found by this TE (defect traceability)

**Sprint derivation:** A TE's sprint is derived from its linked stories. If TE `tests` story PD-5228 and PD-5228 is in Sprint 28 (via SprintMembership), the TE belongs to Sprint 28. If a TE links to stories in multiple sprints, it belongs to the most recent sprint.

### 4.3 TestRun

The individual result of running one test within one execution. This is where pass/fail lives. Fetched from the Xray GraphQL API (not accessible via Jira API).

```
TestRun
├── Id              string (Xray test run ID, PK)
├── ExecutionIssueId string (FK → TestExecution.IssueId)
├── Status          enum (PASS, FAIL, TODO, EXECUTING, ABORTED)
├── StatusName      string (display name from Xray)
├── StartedAt       DateTime (nullable)
├── FinishedAt      DateTime (nullable)
├── ExecutedById    string (nullable — who executed this specific run)
```

### 4.4 TestSet

Represents a Test Set issue from Xray, used to group tests by feature area. Linked to stories/requirements via the `tests` link type.

```
TestSet
├── IssueId         string (Xray internal ID, PK)
├── IssueKey        string (Jira issue key, e.g., "PD-4019")
├── Summary         string (e.g., "v6 | Dashboard", "v6 Verification")
├── AssigneeId      string (FK → Developer.AccountId)
├── Status          string
```

Test Sets are read for context (feature area grouping) but are not the primary analytics entity — Test Executions with their test runs drive all QA metrics.

### 4.5 Entities NOT modeled

- **XrayTestCase** — removed. The "Test" issue type exists in Xray but the team creates zero Test issues. All testing flows through Test Executions directly.
- **XrayTestPlan** — removed. Test Plans exist (5 total) but have no issue links to epics or stories. Named by version/milestone convention only. Cannot be traversed programmatically. Deferred until the team establishes a linking convention.
- **QaMember** — removed. The audit showed QA and developer roles overlap (Taylor executes tests and is assigned bugs; Mateusz does both dev stories and test executions). Reusing the Developer entity avoids duplication. The QA analytics page filters by "developers who have TE assignments."

## 5. Features

### 5.1 Ticket-Level Test Enrichment

**Question:** "Is this ticket tested? How well?"

For every ticket in a sprint, enrich with:
- **TE count** — how many Test Execution issues are linked via the `tests` link type
- **Test run results** — for each linked TE, the test runs inside it and their statuses (PASS/FAIL/TODO/EXECUTING). Fetched from Xray GraphQL API.
- **Test coverage status:**
  - **Passed** — has linked TEs and all test runs are PASS
  - **Failed** — has linked TEs and at least one test run is FAIL
  - **In Progress** — has linked TEs with TODO or EXECUTING runs
  - **No Tests** — no linked Test Execution issues
- **Pass rate** — of the test runs across all linked TEs, what percentage passed
- **Bugs found** — count of bugs linked to TEs via `Blocks` link type (defect traceability)

This enrichment is the foundation — all other QA metrics aggregate from it.

**Edge cases:**
- Ticket with multiple linked TEs, some passing, some failing → show both counts, overall status is the worst result
- TE linked to multiple tickets → counts for each ticket independently
- TE with multiple test runs → all runs count; status is the worst across all runs
- Sub-tasks → inherit parent ticket's test coverage for aggregation, but can have their own linked TEs
- TE with status "Cancelled" (e.g., PD-4359) → excluded from metrics

---

### 5.2 Sprint Test Coverage

**Question:** "How well tested is this sprint?"

**Metrics:**
- **Coverage rate** — tickets with at least one linked TE / total feature tickets in sprint × 100
- **Execution rate** — tickets with at least one completed TE (status Done) / tickets with linked TEs × 100
- **Pass rate** — test runs with PASS status / total executed test runs across all sprint TEs × 100
- **Untested tickets** — list of tickets with no linked TEs (the coverage gap)
- **Failing tickets** — list of tickets where any linked TE has FAIL test runs
- **Bugs found** — total bugs discovered via `Blocks` links from TEs in this sprint

**Display:**
- Three metric cards on the Dashboard (alongside existing delivery cards): Coverage %, Execution %, Pass Rate %
- Each card has delta vs. prior sprint and 4-sprint sparkline (same pattern as v1 delivery cards)
- RAG coloring based on configurable thresholds
- Expandable list of untested and failing tickets

**Health score integration:**
- Add a "Quality" sub-score to the existing sprint health score
- Weighted combination of coverage rate + pass rate
- Configurable weights and thresholds (same pattern as existing health score)

**Health score thresholds (configurable defaults):**

| Metric | Green | Amber | Red |
|---|---|---|---|
| Coverage rate | ≥ 80% | 50-79% | < 50% |
| Pass rate | ≥ 90% | 70-89% | < 70% |

---

### 5.3 Cross-Sprint QA Trends

**Question:** "Is our quality improving or declining over time?"

**Metrics (all trended across sprints):**
- Coverage rate trend — are we testing more of our stories over time?
- Pass rate trend — are tests passing more consistently?
- TE volume trend — total Test Executions per sprint (is testing effort growing?)
- Bugs-found-in-testing trend — bugs linked via `Blocks` per sprint (are we catching more before release?)
- Defect correlation — sprints with low coverage rate vs. bug ratio from v1 (F13)

**Display:**
- Multi-line chart: coverage rate (blue), pass rate (green), execution rate (gray) across N sprints
- Correlation view: overlay coverage rate with bug ratio (from v1 Bug Ratio feature) — visualize whether low coverage correlates with more bugs in subsequent sprints
- Same sprint selector and sub-team filter as v1 (cross-cutting concerns C2, C3)

---

### 5.4 Per-Developer Story Quality

**Question:** "Whose stories are consistently well-tested and passing?"

**Metrics (per developer, per sprint):**
- Stories with test coverage — how many of this developer's stories have linked TEs
- Coverage % — covered stories / total stories for this developer
- Pass rate — of test runs on their stories, what percentage passed
- Untested story count
- Bugs found — bugs discovered via TEs on their stories (via `Blocks` links)

**Display:**
- Table on Developers page (new tab or column extension): Developer | Stories | Covered | Coverage % | Pass Rate | Bugs Found
- Cross-sprint trend per developer
- Flag: developer with coverage rate below team average for 2+ consecutive sprints

**Note:** This measures test coverage of their stories, not who executed the tests. A developer with low coverage might indicate QA prioritization gaps or stories that are hard to test.

---

### 5.5 QA Workload & Throughput

**Question:** "How is testing work distributed across the team?"

**Metrics (per person, per sprint):**
- Test Executions assigned — how many TEs this person owns
- Test runs completed (total, PASS, FAIL)
- Execution throughput — test runs per sprint
- Stories covered — unique tickets whose TEs this person is assigned to
- Bugs found — bugs linked from TEs this person owns

**Display:**
- Dedicated QA page (new sidebar entry) with table: Person | TEs Assigned | Runs Completed | Pass/Fail Split | Stories Covered | Bugs Found
- Workload distribution chart — stacked bar showing each person's TE volume per sprint
- Cross-sprint throughput trend (line chart, same pattern as developer throughput)
- Workload balance indicator — flag when one person handles >50% of all executions

**Edge cases:**
- TE with no assignee → attribute to "Unassigned"
- Person who is also a developer → appears in both Developer throughput and QA workload pages. Same Developer entity, different analytics lens.
- Multiple people involved in same TE → attribute to the TE assignee (single owner)

**Current state:** The audit shows Taylor handles 9 of 10 TEs and Mateusz has 1. The workload balance flag would fire immediately — useful data for the team.

---

### 5.6 Test Execution Timeline

**Question:** "When were tests executed relative to the sprint lifecycle?"

**Metrics:**
- Test execution dates plotted against sprint start/end dates
- Early testing (first half of sprint) vs. late testing (second half)
- Tests executed after sprint close (post-sprint testing)
- Gap between ticket completion (cycle time end) and test execution

**Display:**
- Timeline chart: horizontal bars showing when test executions happened within each sprint
- Highlight zones: planning period, development period, testing crunch (last 2 days)
- Correlation with disruption: overlay test execution timeline with scope addition timeline (from v1 Scope Change feature)
- Flag: tickets completed but not tested by sprint close

---

### 5.7 Epic Test Health

**Question:** "How well tested is this epic overall?"

Since Test Plans are **not linked to epics** (audit confirmed: all 5 Test Plans are standalone with no issue links), epic test health is derived bottom-up from the stories within the epic and their linked TEs.

**Metrics (per epic):**
- Story coverage within the epic — which stories have linked TEs, which don't
- Epic coverage rate — covered stories / total stories in epic × 100
- Epic pass rate — aggregated test run results across all TEs for stories in this epic
- Bugs found in epic — bugs linked via `Blocks` from TEs on this epic's stories

**Display:**
- Extension to the existing Epic Progress page (v1 F14): add QA columns to the epic table
- Columns: Coverage % | Pass Rate | Bugs Found
- Expandable detail: per-story test status within the epic
- Progress bar showing test coverage alongside development completion

### 6.1 Navigation Changes

Add to sidebar:
- **QA** — QA member workload, execution throughput, test timeline (new page)

Extend existing pages:

### 6.2 Settings Changes

New settings section (visible only when Xray is enabled):

- **Xray Credentials** — Client ID + Client Secret fields
- **Connection test** — "Test Connection" button that authenticates and confirms access
- **Quality Health Thresholds** — coverage rate and pass rate thresholds for RAG coloring (same pattern as existing health thresholds)

### 6.3 Conditional UI

When Xray is disabled:
- No QA page in sidebar
- No QA cards on Dashboard
- No QA columns on Developers or Epics pages
- Health score computed from delivery metrics only (same as v1)
- Settings shows only the Xray toggle — credentials and thresholds hidden until enabled

When Xray is enabled but not yet synced:
- QA sections show empty states with "Sync sprint to load QA data" prompt
- Health score excludes Quality sub-score until first QA sync completes

## 7. Tech Stack

### 7.1 Additions to v1 Stack

| Layer | Addition | Reasoning |
|---|---|---|
| Xray Client | Typed HttpClient for GraphQL | Same pattern as existing JiraClient — typed HttpClient, DI-registered, with auth token management |
| GraphQL | Raw HTTP POST with JSON payloads | No GraphQL client library needed — Xray's API is simple enough for hand-crafted queries. Avoids dependency bloat. |
| Token Management | In-memory token cache with 23-hour TTL | Bearer token expires at 24h. Refresh proactively at 23h. No persistent token storage needed. |
| Database | Same SQLite | New tables for Xray entities. Same EF Core patterns. |

### 7.2 What Doesn't Change

- Same .NET / EF Core / SQLite / Vue / Pinia / Tailwind / ApexCharts stack
- Same sync pattern (manual trigger, idempotent, upsert)
- Same analytics pattern (compute on the fly, delta vs prior sprint, sparklines)
- Same cross-cutting concerns (sub-team filter, multi-sprint selection)

## 8. What's Deferred (v3+)

- **Automated test integration** — importing results from CI/CD pipelines (JUnit, Cucumber). Current scope is manual testing only.
- **Test flakiness detection** — tracking tests that flip between PASS and FAIL across executions. Requires execution history depth.
- **Deep defect traceability** — full chain from FAIL test run → specific step that failed → bug created. Basic bug-TE linking via `Blocks` is in scope (§5.1); deeper step-level traceability is deferred.
- **Test case quality metrics** — how well-written are the tests themselves (step count, coverage depth). Subjective and out of scope.
- **Xray Server/DC support** — REST API only, different entity model. Cloud-only for now.
- **Multi-project Xray support** — tests across multiple Jira projects. Current scope assumes single project.
- **Test Set analytics** — regression vs. smoke vs. feature test breakdowns. Team organizes Test Sets by feature area (Dashboard, Verification, Green Bean, etc.) — could categorize once naming conventions stabilize.
- **Test Plan linking** — Test Plans are currently standalone (no epic/story links). If the team establishes a linking convention, Fokus could surface test plan progress directly.
- **QA capacity planning** — predicting how many test executions are needed per sprint based on historical data.
- **Requirement coverage matrix** — full traceability matrix (requirement → test → execution → defect). Xray has this natively — Fokus would only add sprint-level aggregation.

## 10. Resolved Questions (from Xray audit)

1. **Test Execution → Sprint linking** — Sprint field on TEs (`customfield_10020`) exists but is inconsistently populated (1 of 10 TEs had it). **Resolution:** Derive sprint from linked story's sprint membership. TE `tests` Story → Story is in Sprint N → TE belongs to Sprint N.

2. **QA member identification** — Taylor (9 TEs) and Mateusz (1 TE) are the test executors. Both also appear on Bugs and Stories. **Resolution:** Reuse the Developer entity. No separate QaMember. QA page filters by "developers with TE assignments."

3. **Test Plan → Epic linking** — All 5 Test Plans have zero issue links. Named by version/milestone convention (v5 E2E, v6 Blue Ocean). **Resolution:** Test Plans are not traversable. Epic test health derived bottom-up from stories → TEs instead.

4. **Standalone Test issues** — "Test" issue type is registered but 0 instances exist. **Resolution:** Removed XrayTestCase entity. All testing flows through Test Executions and Test Sets linked directly to stories.

5. **Bug traceability** — TEs use `Blocks` / `is blocked by` links to connect discovered bugs (e.g., PD-5384 → 3 bugs). **Resolution:** Include bug count in ticket enrichment and sprint metrics. Read `Blocks` links from Jira API during sync.

6. **Test Set organization** — Test Sets group by feature area (Dashboard, Verification, Green Bean, on-device POG, Upload reports). Linked to stories/requirements via `tests` link type. **Resolution:** Store Test Sets for context but TEs drive metrics.

## 11. Open Questions

1. **Xray license tier** — Standard (300 req/5min) or Enterprise (1,000 req/5min)? Affects sync batching strategy. Assume Standard until confirmed.
2. **Historical QA data** — when backfilling past sprints, should we also pull Xray data for them? Older TEs (pre-Sprint 28) have no sprint field and inconsistent story links.
3. **Quality health weight** — default 20% for Quality sub-score in health score. Configurable — but is 20% a good starting point?
