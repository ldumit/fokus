## Architect Lessons
- [APPLIED] The "endpoints never touch DbContext directly" guideline creates tension for cross-aggregate read queries. The existing repositories are aggregate-scoped (TicketRepository, SprintRepository). For analytic queries that join across aggregates, the cleanest approach is adding the query method to the repository that owns the primary data (TicketRepository for StatusTransitions), since that repository already accesses DbContext internals (see ReplaceTransitionsAsync). An alternative would be a dedicated read-model query class, but that pattern doesn't exist in the codebase yet and would be premature for one query.
- [TRACKED] The architecture doc's Gaps table already identifies "Workflow auto-detection" as too domain-specific for a reusable skill. Confirmed: the forward-flow scoring algorithm is bespoke to this feature. Full inline detail in the plan step was the right call.
- [TRACKED] For focused operation services with no infrastructure dependencies (pure algorithmic logic), there's a design tension between static utility methods and DI-registered classes. Chose DI-registered class for consistency with SprintIssueSyncService pattern, even though it has no constructor dependencies. This makes it testable via the same patterns as other services.
- [TRACKED] When a plan step says "registered in DI via AddScoped" but does not explicitly list `DependencyInjection.cs` in the "Files to modify" section, the developer must infer this. Future plans should always list the DI registration file explicitly when a new class requires DI wiring — it is a file modification, not an implicit side effect.
- [TRACKED] Step 1 done checks benefit from a file inventory cross-check (plan's listed files vs implementation's reported files). Any extra file in implementation that is not in the plan should be either (a) justified by an implicit plan requirement or (b) flagged as scope creep. In this case, `DependencyInjection.cs` was justified.
- [APPLIED] When a plan names a store action (e.g., `detectWorkflowStages()`), enforce the exact name or require the developer to document the rename as a deviation. The reviewer caught `runDetectWorkflowStages()` as an undocumented deviation -- this is avoidable with a plan-writing convention: "Named identifiers in the plan are the contract; renaming is a deviation requiring documentation."
- [TRACKED] Plans that specify a function for a specific user action (like `removeSidelinedStatus` for dismiss-without-add) should also specify the UI trigger. Step 5 defined the function but Step 6 only wired the "+" button for `moveSidelinedToStages`. The dismiss path had no UI entry point, creating dead code. Lesson: every plan-specified action needs a corresponding UI wireup step, or should be explicitly deferred.
- [APPLIED] Guard consistency across parallel code paths: when the plan describes two paths that populate the same form field (auto-detect on mount vs manual Re-detect), specify the guard conditions for both. The auto-detect path had `stages.length > 0` but the Re-detect path did not, causing silent data loss on empty results. Future plans should call out guard parity explicitly when multiple paths write to the same state.

## Developer Lessons
- [APPLIED] When a store action is described as "appends to the workflow stages list in the form", that form state lives in the view, not the store. The store action should only mutate store-owned state (the sidelined list); the view handler does the form mutation. Conflating these causes the store to mutate persisted `settings.workflowStages` which breaks the proposal-vs-saved separation.
- [APPLIED] For detection empty-state UI, guard against flickering by checking all three conditions together: `form.workflowStages.length === 0 && detectionResult === null && !detecting`. Without the `!detecting` guard, the empty-state message flashes during the auto-detect call on mount.
- [TRACKED] The bash shell in this environment is POSIX bash, not PowerShell -- use forward-slash paths (`/d/src/...`) and pipe to `tail`, not `Select-Object -Last`.
- [APPLIED] EF Core `Contains` on a fetched `List<string>` of IDs translates to SQL `IN (...)` correctly. For very large sets this would need batching, but the Fokus dataset is bounded.
- [APPLIED] Skill gap: No frontend Pinia store extension skill exists. Pattern: what state belongs in the store vs the view form, async loading flags, action naming. Suggested name: `pinia-store-patterns`.
- [APPLIED] Skill gap: No Vue 3 view-form pattern skill exists. Pattern: reactive form local to view, `syncFromStore()` on mount, optimistic form mutation vs persisted store state. Suggested name: `vue-view-form-patterns`.

## Reviewer Lessons
- [APPLIED] When a plan defines a store action by name (e.g., `detectWorkflowStages()`), renaming it in implementation (e.g., `runDetectWorkflowStages()`) is a deviation that should be listed in implementation.md. "None" in Deviations from Plan should be verified against all named identifiers in the plan, not just structural changes.
- [TRACKED] Dead-code functions that were specified in the plan but have no UI trigger are a conformance gap, not just a style issue. Check that every plan-specified action/function is reachable from the UI, not just present in the store.
- [APPLIED] When reviewing a "replace with fresh proposal" flow, check whether the replacement guard (`stages.length > 0`) is applied consistently between the auto-detect path and the manual re-detect path. The two paths often diverge in practice.
- [TRACKED] Pre-commitment predictions are effective: predicting "identical function bodies" and "name mismatch" before reading the code leads to deliberate targeted search rather than passive reading. All five predictions were confirmed or clarified.
