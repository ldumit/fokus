# Sprint Summary Card — Lessons

## Architect Lessons
- [APPLIED] The `docs/architecture/v1.md` file referenced in the agent instructions does not exist. All architectural decisions live in the project `CLAUDE.md` and service `CLAUDE.md`. Future references to "architecture doc" should point to these files, or the architecture doc should be created.
- [TRACKED] When a feature is computation-heavy with no domain model changes and no migrations, the plan naturally clusters into three bands: repository queries, computation service, endpoints. Keeping the computation service as a pure function over data (no DB access) makes it testable and reusable -- this should be the convention for all analytics features.
- [TRACKED] The spec's BR18 (zero-SP developers) says "active developer assigned to the sprint" but the domain model has no direct sprint-developer assignment. The interpretation "developer is assignee on at least one non-removed membership ticket" is the only one that works with the data model. When specs reference relationships that don't exist in the domain model, the plan should document the interpretation explicitly.
- [APPLIED] The `extract-feature-service` skill maps well to analytics computation services, but the existing skill description focuses on extracting from endpoints. Analytics services are created fresh (not extracted). The skill still applies for naming and placement conventions. Worth noting for skill improvement.
- [APPLIED] Frontend steps (7-11) all map to "None" disposition in the skill mapping -- there is no frontend skill coverage at all. This is a significant gap that will compound across F9-F14. Logging for future skill creation.
- [TRACKED] The cross-cutting patterns (C1 delta, C2 sub-team filter) are deliberately implemented inside `SprintSummaryService` rather than as separate abstractions. The first feature should prove the pattern concretely before extracting reusable utilities. F9 or F10 planning should assess whether extraction is warranted.
- [TRACKED] Step 1 done check for this feature was clean — all 11 steps covered, two minor deviations both explained. Pre-commitment predictions (PageToolbar under-reporting, sparkline deviations, silent computation simplifications) did not materialize. For computation-heavy features with a detailed plan, the done check is straightforward when the plan is specific about file paths and responsibilities per step. The plan's specificity paid off here.
- [TRACKED] Pipeline closed in 1 review cycle (no CRITICAL/HIGH). The two MEDIUM findings (unused parameter via closure, `First` without null guard) are both patterns that a plan cannot prevent — they are code-level decisions the reviewer catches. The plan's job is domain correctness; the reviewer's job is code hygiene. This division worked well.
- [TRACKED] The spec's display format example ("24 / 30 SP") was illustrative but the plan did not lock down the exact `DisplayValue` format string for each metric. The implementation simplified to just the completed number. Future plans for UI-heavy features should specify display format strings explicitly when the spec provides examples, or explicitly mark them as "illustrative, developer's discretion."
- [APPLIED] Reviewer's gap analysis surfaced two UX gaps not in the plan: error state not rendered in the view (store tracks `error` but view ignores it), and no empty-state message when sub-team filter produces zero developers. Both are valid omissions for v1 but should be captured as follow-up items. Plans for store-backed views should include a step or note for error/empty rendering.

## Developer Lessons

- [TRACKED] `SprintState` enum is in `Jira.Contracts` namespace, not `Fokus.Domain`. The Persistence project's GlobalUsings only imports `Fokus.Domain`. When writing new repository methods that reference `SprintState`, add `global using Jira.Contracts;` to `Fokus.Persistence/GlobalUsings.cs`. The transitive assembly reference exists (Persistence → Domain → Jira.Contracts) so no csproj change is needed.
- [APPLIED] `ThenInclude` chains in EF Core: when loading `Sprint → Memberships → Ticket → Assignee`, each `ThenInclude` continues from the last included navigation. Pattern: `Include(s => s.Memberships).ThenInclude(m => m.Ticket).ThenInclude(t => t.Assignee)`.
- [APPLIED] Vue `withDefaults` + `defineProps` is the correct pattern for components with optional props with defaults in `<script setup>`.
- [APPLIED] PageToolbar `<select>` elements need `appearance-none bg-transparent` Tailwind classes so native browser select styling doesn't override the custom-styled container div.
- [APPLIED] Missing skill: frontend patterns (types in index.ts, apiFetch API modules, Pinia composition stores, Vue prop/emit with withDefaults). Suggested name: `frontend-patterns`. Reference files: `client/src/types/index.ts`, `client/src/api/settings.ts`, `client/src/stores/settingsStore.ts`, `client/src/components/PageToolbar.vue`.
- [TRACKED] Missing skill: ApexCharts sparkline configuration in Vue 3, RAG color class mapping, URL query param sync with Pinia store. Suggested name: `dashboard-view-patterns`.

## Reviewer Lessons

- [TRACKED] Dead parameters in private service methods are easy to miss during implementation — when a parameter is threaded through multiple call sites but only used via closure in a lambda, it looks used but isn't. Check method bodies separately from call sites.
- [TRACKED] For analytics computation services with many pure-function private statics, pre-commitment predictions about business rule implementation (BR16, BR17, BR18, C1, C2) are high-value checks. Verify each rule's guard condition against the exact domain model fields (e.g., `WasCommitted`, `RemovedAt`, `AddedAt`) rather than trusting naming alone.
- [APPLIED] `First` vs `FirstOrDefault` at service boundaries: even in single-user SQLite apps, a `First` call on a bulk-loaded list based on an ID determined earlier is worth flagging as MEDIUM — the failure surface is small but the error is an unhandled 500 with no diagnostic message.
- [APPLIED] Frontend leaderboard visibility guard (`v-if="list.length > 0"`) can silently swallow sub-team filter edge cases where a sub-team has no developers. Gap analysis should always consider what the UI shows (or fails to show) when filter cross-products produce empty results.
- [APPLIED] Error state (store tracks `error`) not surfaced in view is a recurrent gap in Pinia store + Vue view combinations. Add this to the standard frontend gap checklist.
- [TRACKED] Inaccurate deviation notes in implementation.md (claiming a GlobalUsings change that was already there) should be noted as LOW — they mislead future reviewers about what actually changed.

## PO Lessons
- [TRACKED] Critic caught the asymmetry between explicit carry-over rate formula (BR9) and missing disruption/completion rate formulas. All metric formulas in a spec should be stated with equal explicitness — don't assume the reader will cross-reference v1.md for some formulas but not others.
- [TRACKED] When simplifying a v1.md concept (e.g., "high-disruption days" became "mid-sprint disruption" with a 2-day grace period), explicitly acknowledge the simplification in Out of Scope and forward-reference the feature that owns the full version (F10). Silent simplifications look like oversights.
- [TRACKED] Sparkline BR12 had a contradictory sentence ("doesn't change based on the sprint selector" vs "ending at the selected sprint"). Self-review should catch internal contradictions within the same business rule — read each rule as a standalone statement.
- [APPLIED] When asking clarifying questions during shaping, offer the user the choice: "Want me to research these or will you answer?" Don't silently go research, and don't force blind answers. (Now captured in `.claude/rules/research-before-asking.md` as a cross-agent rule.)
